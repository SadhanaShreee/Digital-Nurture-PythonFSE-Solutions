Task 1: Map Testing Types to a Real System
1. Test cases by test level
Test Level	Description	Example Test Case
a. Unit Testing	-> Tests a single function/method in isolation, with dependencies mocked out
Test the validate_course_name() function directly

b. Integration Testing	-> Tests two or more components working together.	
Call the create_course() service function and verify it correctly inserts a row into the courses table via the ORM

c. System Testing	-> Tests a full end-to-end flow, from the API request all the way to the database response.	Send a POST /api/courses/ request with a valid JSON payload through the actual running server, 
and verify the HTTP response (status code, response body) and that the record now exists when queried back via GET /api/courses/{id}.

d. User Acceptance Testing (UAT)	-> Tests from the perspective of an actual end user, against real-world workflows rather than technical specs.
	A college admin logs in, creates a new course called "Data Structures", assigns it to a department, and confirms it appears correctly in the course listing page 
    matching what they'd expect in day-to-day use.


2. Functional vs Non-Functional classification

a. Unit: validate_course_name() ->	Functional
b. Integration: create_course() -> inserts into DB correctly -> Functional
c. System: POST /api/courses/ end-to-end flow -> Functional
d. UAT: admin creates and views a course -> Functional


3. Black-Box vs White-Box Testing
Black-Box Testing: Testing the system purely from the outside, based on inputs and expected outputs, 
          with no knowledge of the internal code. You only know the API contract (e.g., "POST /api/courses/ should return 201 on success")
          not how it's implemented internally.

White-Box Testing: Testing with full knowledge of the internal code ->  you look at branches, conditions, and logic paths to design
                   tests that exercise specific lines of code (e.g., making sure both the if and else branch of the validation 
                   function are covered).

Task 5:
New: Tester logs the defect after finding it; not yet reviewed.
Assigned: A lead/manager reviews the defect and assigns it to a developer.
Open: Developer acknowledges the defect and begins working on it.
Fixed: Developer has made a code change believed to resolve the issue and moves it back to QA.
Retest: Tester re-executes the original steps to reproduce the bug against the fix.
Verified: Tester confirms the fix works as expected and the bug no longer occurs.
Closed: Defect is formally closed out; no further action needed.

Task 8:
Severity measures how badly the defect impacts the system's functionality - technical impact. 
Priority measures how urgently it needs to be fixed - business/scheduling impact. 
They're independent and don't have to move together.

Real-world example where High Severity ≠ High Priority: 
Suppose the Course Management API has a bug in a rarely-used "export course history to legacy XML format" feature 
used by exactly one internal integration that's being decommissioned next month, and calling it crashes the whole export module.
That's High Severity (a whole feature crashes), but Low Priority — because the feature is about to be retired anyway, 
there's no business value in fixing it before then. The team would rather spend that time on something users actually depend on.
